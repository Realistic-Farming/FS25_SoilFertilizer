fix: stop the deferred fill-type init reporting a failure it never established

A healthy singleplayer load prints two alarming warnings and the feature works
perfectly. That is a false-bug-report generator, and one report has already been
read as a map compatibility problem. Three defects, one surface.

THE GIVE-UP WAS UNCONDITIONAL, AND THE BUDGET WAS NEVER THE MECHANISM.

The dispatch described the 120-retry budget burning in 114ms. It is worse than
that: the budget was never spent at all. `_deferredRetryCount = 121` was assigned
as a "stop" sentinel once spray types completed, and the unconditional `+ 1` at
the top of the next tick walked it to 122, which WAS the give-up branch. Success
and failure therefore reached the same warning, on every load, having retried
zero times.

The proof is in the log rather than in reading the control flow. Each warning
appears exactly once, and SoilLogger.warning has no deduplication (Logger.lua:135
prints every call), so the loop body ran a single tick. Raising 120 to any number
would not have changed one line of that.

From the 2026-09-21 session log:
  19:49:55.179  reapplyFillUnitPatch reports unavailable, and spray types report
                64 registered with 0 skipped, so _sprayTypesComplete became true
  19:49:55.293  "still unavailable after 120 retries"
  19:51:24.700  Entered Gameplay, ie. isMissionStarted becomes true only HERE
  19:51:28.150  the dependency actually arrives: 13 solid + 49 liquid detected
  19:51:28.151  Hook installation complete: 33/33 successful, 0 failed

Both warnings preceded the mission by about 89 seconds and the thing they were
waiting for by 93.

The retry now ends on the real completion signal, spray types complete AND the
fill unit re-patch returning true, and the timeout is only a ceiling for a
genuinely broken setup. That ceiling is MISSION time, not frames and not load
time. isMissionStarted is the engine's own signal, set in BaseMission:onStartMission
(BaseMission.lua:247) beside the "Entered Gameplay" line, its only other writer
being the false initialiser at :56. isRunning is NOT that signal: BaseMission.lua:53
is one of many writers and AIJob/AITask own the rest. Elapsed ms rather than frames
because a frame budget means a different amount of waiting on every machine while
the dependency arrives on a wall clock. 30s is far above the 3.45s it took here.

The old give-up also set `_sprayTypesComplete = true` to stop the loop, which was
a lie about state to achieve control flow. `_deferredInitDone` does that job now
and nothing false is written.

ZERO NAMES CHECKED WAS REPORTED AS ZERO NAMES FOUND.

reapplyFillUnitPatch iterated `self._fuSolidNames or {}`. That field is assigned
from a 13-name literal in installFillUnitHook, so once that has run it is never
legitimately empty; before it runs the field is nil and the `or {}` made the loop
body execute zero times. `found` stayed 0 with missingNames empty, and the
`found == 0` branch announced "custom fill types still unavailable (missing: )"
with nothing after the colon. The empty list in the real log is that bug showing
through. It now returns early with a debug line when the hook has not installed,
so `found == 0` keeps meaning we looked and nothing was registered. That branch
still warns, and still names what it looked for.

THE TEXT INVENTED A DIAGNOSIS.

It volunteered "dedicated server or modded map may have incomplete fill type
loading". Nothing at that point had established either, and that guess is why a
night went into a fill-type cap that was never involved; the engine's own cap
error appears zero times across six sessions. The message now states elapsed
mission time, sprayTypesComplete, the re-patch result, whether the hook ever
installed, and that it establishes no cause.

The block is lifted out of update() into _updateDeferredInit so a test can drive
it. update() runs a dozen unrelated systems past this point and a bar that had to
survive all of them to reach its assertions would be testing those instead.

EVIDENCE. Suite 5340 passed, 0 failed across 100 files, up from 5304 across 99.
The new bar is 36 assertions driving the real _updateDeferredInit and the real
HookManager:reapplyFillUnitPatch.

tools/test/mutate_deferred_init.py runs four mutants, each restoring one real
property of the old code rather than an arbitrary edit: the `or {}` iteration, the
missing isMissionStarted gate, the invented diagnosis, and completion keyed only
on spray types while ignoring the re-patch result. All four killed, 0 survived, 0
unapplied, and both sources verified byte-identical after restore by sha256. It
aborts rather than reporting a survivor if a mutation fails to apply, because a
no-op edit and an unpinned rule look identical from the outside.

Built and deployed. No in-game run, so no log.txt evidence from this branch.
